# DORASANI Security & Data Protection Specification

This document outlines the security architecture, Row Level Security (RLS) policies, authentication boundaries, and data protection measures implemented across the **DORASANI** platform.

---

## 1. Threat Modeling & Security Principles

1. **Defense in Depth:** Security is enforced at the database level using PostgreSQL Row Level Security (RLS) rather than relying exclusively on frontend or API checks.
2. **Principle of Least Privilege:** Anonymous callers have read-only access to published catalog items. Customers can only read and modify their own carts, orders, and addresses.
3. **No Privilege Escalation:** Customer users cannot self-assign administrative roles. Role assignment is restricted to `super_admin` or trusted database functions.
4. **Secret Isolation:** Service role secrets and database passwords never reside in client bundles or public repositories.

---

## 2. Row Level Security (RLS) Policies

RLS is enabled on **all 39 public tables**. Key policies include:

### Products & Categories (`products`, `product_variants`, `product_media`, `categories`)
- **`SELECT` (Public):**
  ```sql
  CREATE POLICY "Public products viewable" ON public.products
    FOR SELECT USING (status = 'active');
  ```
- **`INSERT / UPDATE / DELETE` (Admin Only):**
  ```sql
  CREATE POLICY "Admins manage products" ON public.products
    FOR ALL USING (public.is_admin());
  ```

### Customer Profiles (`profiles`)
- **`SELECT`:** Any authenticated user can view their own profile; admins can view all profiles.
  ```sql
  CREATE POLICY "Users view own profile" ON public.profiles
    FOR SELECT USING (auth.uid() = id OR public.is_admin());
  ```
- **`UPDATE`:** Users can only update non-sensitive personal fields in their own profile.
  ```sql
  CREATE POLICY "Users update own profile" ON public.profiles
    FOR UPDATE USING (auth.uid() = id);
  ```

### User Roles (`user_roles`)
- **`SELECT`:** Authenticated users can read their own assigned roles.
- **`INSERT / UPDATE / DELETE`:** STRICTLY restricted to `super_admin`.
  ```sql
  CREATE POLICY "Super admins manage roles" ON public.user_roles
    FOR ALL USING (public.has_role('super_admin'));
  ```

### Customer Addresses (`customer_addresses`)
- Customers can create, view, update, and delete only their own shipping addresses.
  ```sql
  CREATE POLICY "Users manage own addresses" ON public.customer_addresses
    FOR ALL USING (auth.uid() = user_id);
  ```

### Orders & Order Items (`orders`, `order_items`)
- **`SELECT`:** Customers can only inspect orders matching their `user_id`. Administrators can view all orders for fulfillment.
  ```sql
  CREATE POLICY "Users view own orders" ON public.orders
    FOR SELECT USING (auth.uid() = user_id OR public.is_admin());
  ```
- **`INSERT`:** Executed safely via the `SECURITY DEFINER` atomic function `process_checkout_atomic()`, ensuring validation, row locking, and inventory decrement occur within a single transaction.

### Inventory Ledger (`inventory_movements`)
- Append-only ledger. Read access is restricted to `inventory_manager`, `admin`, and `super_admin`. Deletes are prohibited.

## 3. Atomic Checkout & Concurrency Protection

To prevent race conditions during high-demand festival flash sales (e.g., Diwali or Sankranti offers):
- The `process_checkout_atomic` function executes with `FOR UPDATE` pessimistic row locking on target products.
- Stock availability is evaluated under lock before decrements occur.
- If two patrons attempt to purchase the final Kanjivaram saree concurrently, the second transaction is safely rolled back with an informative out-of-stock notification.
- An `idempotency_key` unique constraint prevents duplicate order creation if network retries occur.

---

## 4. Payment Gateway & Webhook Security

- **Webhook Signature Verification:** The `payment-webhook` Edge Function inspects the cryptographic HMAC SHA-256 signature generated by Razorpay/Stripe using a server-side secret (`PAYMENT_WEBHOOK_SECRET`).
- **Idempotent State Changes:** Orders can only transition from `pending` to `paid`. Repeated delivery of the same webhook payload produces a 200 OK without double-recording transactions or stock adjustments.

---

## 5. Compliance & Data Privacy (DPDP Act)

- Customer phone numbers, delivery addresses, and order histories are stored strictly for order fulfillment and taxation compliance.
- WhatsApp communication preferences (`whatsapp_opt_in`) are respected before triggering automated dispatch notices.
